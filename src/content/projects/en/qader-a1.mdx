## 01 — Context & Motivation

Qader A1 was my first full end-to-end engineering project at Benha University, where I owned the entire software stack. The team started with an **Arduino Uno + IR receiver prototype (V1)** built partly from recycled hardware components.

Infrared remote control proved the chassis and motors worked, but it immediately hit physical limits: line-of-sight dropouts, no live sensor feedback, and no way to visualize what the ultrasonic sensor was seeing while driving. Moving to **V2 on an ESP32** turned the robot into a self-hosted Wi-Fi control and telemetry node.

## 02 — System Architecture

Instead of relying on an external backend or mobile app store build, the ESP32 itself hosts the control surface over its local Wi-Fi access point:

- **Browser Radar UI (HTML/CSS/JS)**: Renders real-time ultrasonic distance sweeps, directional drive controls, speed tuning, laser toggle, and return-to-start trigger.
- **ESP32 Embedded HTTP Server**: Handles concurrent control commands and telemetry reads directly on the microcontroller.
- **C++ / Embedded C Firmware Loop**: Coordinates servo/ultrasonic sweeping, PWM motor drive, laser actuation, and motion history tracking for return-to-start navigation.

## 03 — Key Engineering Decisions

1. **Embedded Wi-Fi Web Server over Line-of-Sight IR**: Replacing the IR receiver with an ESP32 HTTP control surface allowed sensor sweeps and motor state to stay synchronized in real time from any browser without installing a native client.
2. **Self-Contained Interface Assets**: Serving the HTML/CSS/JS control interface directly from the device removed external network dependencies during live demonstrations at university.
3. **Return-to-Start Navigation**: Tracking movement sequences in firmware enabled an automated return routine rather than purely manual teleoperation.

## 04 — Challenges & Hardware Reality

Hardware removes hand-waving. Power stability across motors and sensors, timing contention between ultrasonic sweeps and HTTP requests, and physical wiring reliability all surfaced during bench testing. Debugging required a multimeter beside the laptop — verifying whether a fault lived in C++ state logic, Wi-Fi request handling, or voltage drop on the chassis.

## 05 — Embedded Security Considerations

Putting physical actuators — drive motors and a laser module — behind a local Wi-Fi HTTP interface was a turning point in how I think about security:

- An unauthenticated local access point means **network reachability equals physical control**.
- Command endpoints on constrained microcontrollers rarely have the memory budget for heavy middleware, which makes explicit state validation and network-layer isolation essential.

That hands-on experience directly informed my later focus on Application Security and IoT/Embedded attack surfaces.

## 06 — Lessons Learned & Future Improvements

- **Lesson**: Owning both firmware and browser UI taught me to trace a request from a button click down to pin voltages — the same end-to-end tracing discipline I use when auditing web APIs.
- **Future direction**: Adding WebSocket telemetry for lower-latency radar frames, explicit command authentication/token checks on the ESP32 AP, and hardware watchdog failsafes to halt motors on connection loss.
